# 解析与生题模型任务并发优化任务说明

## 项目范围

`/Users/ljj/Documents/分析多模态问题/answer_book_platform_v1_v6.8_material_figure_schema_flow_standalone`

## 任务目标

在不改变解析、生题结果语义和流程依赖的前提下，将彼此独立的模型请求改为受控并发，减少整套题目的等待时间。只优化真实存在的串行瓶颈，不为并发拆散必须全局判断的任务，也不进行无关重构。

## 一、本次主要优化：解析系统

### 第一优先级

1. **题面视觉理解按题并发**
   - 当前位置：`app/question_understanding.py`。
   - 不同题目的视觉理解互不依赖，改为最多 2–3 个并发。
   - 工作者只返回单题结果，由主流程按原题顺序统一合并、校验和写入进度文件，禁止多个线程直接修改共享结果或同时写文件。

2. **作图 Schema 规划按题并发，并与前置解析支线并行**
   - 当前位置：`app/figure_schema_planning.py`。
   - 不同作图题的 Schema 规划可按题并发，最多 2–3 个。
   - 该任务只读取原始题面，可在题面视觉理解开始后作为独立后台支线运行；知识规划、教材索引安装、检索和证据选择无需等待它。
   - 在答案生成真正需要 Schema 前统一等待并汇总，不改变原有答案生成输入。

3. **生成图视觉质检按图并发**
   - 当前位置：`app/figures.py` 中生成图视觉审查流程。
   - 每张图独立审查，限制为 2–3 个并发；完成后按题号、图号稳定排序并统一写回。

4. **解析质量模型回修按题并发**
   - 当前位置：`app/audit_model_repair.py`。
   - 多个待修题目可并行请求和单题校验，最后由主流程统一替换 fragment、更新恢复记录并落盘。
   - 单题失败不得取消其他题目的有效回修结果，错误信息仍按题归档。

### 第二优先级

5. **独立作图代码生成按题并发**
   - 当前位置：`app/figures.py`。
   - 初次代码生成和需要重试的代码生成，均可在各自批次内按图并发。
   - 同一张图仍严格保持“代码生成 → 本地校验/渲染 → 失败后图片模型兜底”的先后关系。

6. **图片模型兜底生成按失败图并发**
   - 当前位置：`app/figures.py`。
   - 只有已经确认代码或本地渲染失败的图才进入兜底；不同失败图可并发，同一图不得提前触发兜底。

7. **图件视觉回修候选并发**
   - 当前位置：`app/figures.py`。
   - 同一失败图的“原模型候选”和“视觉模型候选”可以并行，不同失败图之间也可以并行。
   - 每个候选必须使用隔离目录完成“请求 → 校验 → 渲染 → 视觉审查”。全部候选结束后再按固定优先规则选择一个结果，只提升最终选中的候选，不能按完成先后决定，也不能让多个候选互相覆盖。

### 低优先级

8. **公式证据补充复核按题并发**
   - 当前位置：`app/evidence_selection.py` 中公式类证据的补充复核尾段。
   - 主体证据选择已有并发，只处理该尾段仍逐题调用模型的部分；收益有限，放在主要瓶颈完成后实施。

9. **DOCX 模型回修按题并发**
   - 当前位置：`app/docx_model_repair.py`。
   - 不同题目的修复可并发，但该流程仅在 DOCX 审计失败时触发且数量较少，优先级最低。

## 二、生题系统的处理原则

生题系统不需要为了本任务强行增加新的拆分层级：

- 正式生题已经按批次受控并发，保留并核验现有实现即可，相关位置为 `app/exercise_generation.py`。
- 材料分析是整套材料的范围识别和统一分析，蓝图生成是整套题量、知识点、题型和难度的整体设计；两者都不应拆成逐题并发，否则会削弱全局一致性并增加额外合并逻辑。
- 蓝图依赖用户确认后的分析范围和生成策略，不能与材料分析同时执行。
- 用户逐项点击单个蓝图项生成时，不额外制造后台并发；未来只有在增加“批量生成全部蓝图项”功能后，才考虑按蓝图项并发。

同时确认以下解析环节已有并发，不重复改造：

- `app/knowledge_planning.py`：知识规划；
- `app/evidence_selection.py`：主体证据选择与扩展；
- `app/answer_generation.py`：答案生成；
- `app/exercise_generation.py`：正式生题批次。

## 三、统一并发安全要求

1. 使用项目现有的受控并发能力，默认并发数保持保守，可通过配置调整；不要在每个模块各造一套线程框架。
2. 避免嵌套并发叠加。外层已经并发时，内层不得再次放大请求数；同一模型供应商应受统一并发上限约束。
3. 不在线程间共享会记录重试状态等可变信息的模型客户端；每个工作单元使用独立客户端或经确认线程安全的实例。
4. 工作者只读取输入并返回局部结果；共享 JSON、fragment 列表、进度、统计和文件写入统一由主流程处理，或使用明确的锁保护。
5. 所有汇总结果必须按原题号、图号或既定业务顺序稳定排序，不能使用请求完成顺序。
6. 单个请求失败应保留原有重试、降级和错误记录逻辑，不因并发改变成功判定或吞掉异常。
7. 并发数不是越高越好。初始建议模型请求 2–3 并发，并结合供应商限流、超时、失败率和实际耗时再调整。

## 四、实施顺序

建议分阶段完成并分别验证：

1. 题面视觉理解、Schema 后台支线、生成图视觉质检、解析质量回修。
2. 作图代码生成与重试、图片兜底、视觉回修候选。
3. 公式证据补充复核、DOCX 回修。

每一阶段都应先确认输出一致性和错误恢复，再继续下一阶段，避免一次性改动整条流水线后难以定位问题。

## 五、验收要求

- 使用包含多道图文题、作图题和失败回修场景的同一套输入，对比优化前后结果；题目覆盖、顺序、Schema 绑定、图件绑定、答案 fragment 和错误记录不得因完成顺序发生错位。
- 通过调用时间记录证明目标任务存在真实重叠，整套任务耗时有可见下降；同时记录峰值并发数、限流、超时和重试情况。
- 验证单题或单图模型失败时，其它任务仍能完成，原有兜底链路正常执行。
- 验证同一张图的代码生成、渲染、图片兜底依赖顺序未改变，候选目录无覆盖，最终结果选择稳定。
- 验证进度信息可持续更新且文件内容完整，不出现并发写入损坏。
- 验证生题系统现有批次并发未退化，材料分析和蓝图生成仍保持全局任务语义。
- 补充针对并发顺序扰动、部分失败、稳定排序和共享写入的测试，并运行相关现有测试。
- 只修改与本任务直接相关的并发调度、结果汇总、配置和测试；不改提示词业务语义、生成规则、界面流程或输出结构。
- 完成后说明实际修改文件、各环节并发上限、保留的串行依赖、耗时对比和测试结果。
