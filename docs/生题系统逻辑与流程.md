# 生题系统逻辑与流程（当前程序实现）

> 适用代码版本：当前工作区 `answer_book_platform_v1_v6.8_material_figure_schema_flow_standalone`  
> 整理日期：2026-08-01  
> 本文描述的是**代码当前实际执行的逻辑**，不是产品设想。

## 1. 一句话理解

当前生题系统不是把材料一次性交给模型直接出题，而是由程序控制的三段式流程：

```text
提交原题/知识材料
  → ① 分析材料并拆分可选范围
  → 人工确认参与出题的原题/知识单元和生成方式
  → ② 生成可编辑的出题蓝图
  → 人工审查并修改蓝图
  → ③ 按确认后的蓝图分批生成具体题目
  → 程序规范化、检查、保存
  → 页面查看 / 编辑单题 / 重新生成单题 / Word 导出
```

程序负责流程、数量、题型和难度等硬约束；模型负责材料理解、教学设计和题目内容生成。

核心实现位于：

- `app/exercise_generation.py`：材料分析、蓝图设计、正式生题、单题重生、结构规范化。
- `app/practice_inputs.py`：文字、图片、PDF、Word、TXT、Markdown 的解析。
- `app/practice_jobs.py`：后台任务状态与失败恢复。
- `app/practice_store.py`：历史记录保存。
- `app/practice_export.py`：题目卷 Word 导出与正式交付门禁。
- `app/server.py`：HTTP API 与后台线程调度。
- `web/app.js`：前端六阶段交互、人工确认、编辑和导出。

## 2. 两个入口、一个共同内核

### 2.1 按题出题

输入是一道原题或一套题，系统先识别原题结构和考点，再围绕选中的原题生成专项练习。

典型用途：

- 围绕一道错题做基础到进阶训练；
- 从一套试卷选出若干题，做整套专项补强；
- 给每道原题生成一道平行题；
- 给每道原题生成 1～3 道变式题。

请求中使用 `source_mode: "exam"`。

### 2.2 知识点出题

输入可以只有知识点名称，也可以带教材原文、公式、表格、图片或文档。系统把材料拆成知识单元，再生成知识点模拟题。

典型用途：

- 只有“晶胞 / 点阵参数”这类短名称；
- 粘贴教材的一段定义、公式和推导；
- 上传一个章节的 PDF、Word 或图片；
- 选择多个知识单元，整体综合出题或逐单元出题。

请求中使用 `source_mode: "knowledge"`。知识点模式明确要求模型：不要把教材或知识材料误判成真题，也不要假装存在未提供的原题。

### 2.3 共用部分

两个入口最终都调用同一套核心函数：

1. `analyze_practice_source()`：只分析材料，不出题。
2. `plan_practice_set()`：只设计蓝图，不生成具体题干。
3. `generate_practice_from_plan()`：按已确认蓝图生成题目。

差异主要体现在提示内容、范围名称和生成策略解释上。

## 3. 输入阶段：系统实际使用哪些内容

### 3.1 用户输入字段

| 内容 | 字段 | 用途 |
|---|---|---|
| 模式 | `source_mode` | 区分按题出题和知识点出题 |
| 知识点名称 | `knowledge_title` | 知识点模式的主题和历史记录标题候选 |
| 手动输入文字 | `question_text` | 原题文字、知识点名称、教材正文、补充说明 |
| 上传文件 | `source_files` | 图片、PDF、DOCX、TXT、Markdown，前端转为 Data URL |
| 题量 | `count` / `strategy_count` | 决定蓝图和最终生成数量 |
| 难度 | `difficulty` | 单题难度或整套难度分布 |
| 题型 | `question_types` | 用户选择的允许题型；不选时程序随机编排 |
| 补充要求 | `focus` | 训练重点、限制条件、避免超纲等 |
| 出题方式 | `generation_strategy` | 整体综合、一一对应、逐项变式 |
| 每项变式数 | `variants_per_question` | 逐项出题时每个来源生成几题 |
| 选中范围 | `selected_source_questions` | 人工确认后的原题或知识单元 |
| 文本模型 | `provider`、`model` | 无图片时的分析、蓝图和生题模型 |
| 视觉模型 | `vision_provider`、`vision_model` | 有图片时使用的模型 |
| 思考模式 | `thinking` | 传给模型适配层的思考配置 |

前端组装字段的位置：`web/app.js:1717-1759`。

### 3.2 支持的材料类型和解析方式

| 材料 | 程序处理方式 | 最终交给模型的内容 |
|---|---|---|
| 直接粘贴文字 | 加入“手动输入”文本块 | 文本 |
| PNG/JPG/JPEG/WebP | 转为 Base64 Data URL | 图片 |
| PDF | `pdftotext -layout` 提取文本；扫描型 PDF 优先用内置 PDFium（`pypdfium2`）把最多 24 页转 JPEG，系统存在 Poppler 时以 `pdftoppm` 作为回退 | 文本 + 页面图片 |
| DOCX | `python-docx` 提取段落和表格；从 `word/media/` 按正文位置优先提取最多 24 张内嵌图并保留引用编号 | 文本 + 图片 |
| TXT/Markdown | UTF-8 解码，无法解码字符替换 | 文本 |

限制：

- 一次最多 12 个文件；
- 单文件最多 12 MB；
- 总文件大小最多 36 MB；
- 单次材料解析最多保留 24 张分析/参考图片；
- 扫描型 PDF 最多渲染前 24 页，超过部分进入显式诊断，不会伪装成已分析；
- 没有任何文字或图片时直接报错。

对应代码：`app/practice_inputs.py:14-17`、`41-107`、`110-158`。

### 3.3 文本模型与视觉模型如何选择

程序先判断解析结果中是否存在图片：

- **没有图片**：使用 `provider + model`；
- **存在图片**：优先使用 `vision_provider + vision_model`；
- 视觉模型字段为空时，尝试使用该服务商默认视觉模型；
- 选择的服务商不支持视觉能力时立即报错，不继续生成。

因此，PDF 和 DOCX 即使有可提取文本，只要同时提取到了页面图或内嵌图，也会走视觉模型。

对应代码：`app/exercise_generation.py:343-357`。

## 4. 完整流程：六个用户可见阶段、三个后台任务

前端展示六个阶段：

```text
提交 → 分析 → 范围确认 → 蓝图审查 → 生成 → 结果
```

后台实际只有三种任务类型：

| 后台任务 | 核心函数 | 结果 |
|---|---|---|
| `analyze` | `analyze_practice_source()` | 材料范围和整体分析 |
| `plan` | `plan_practice_set()` | 可编辑蓝图 |
| `generate_from_plan` | `generate_practice_from_plan()` | 具体题目并写入历史记录 |

每个阶段都先创建 `generation_时间_随机串` 任务文件，再由后台线程执行。前端约每 1.2 秒轮询一次任务状态。刷新页面后，会尝试从浏览器 `localStorage.activePracticeJobId` 恢复仍在执行的任务。

对应代码：`app/practice_jobs.py:35-57`、`100-125`，`app/server.py:373-394`，`web/app.js:790-857`。

### 4.1 阶段一：提交材料

用户提交原题或知识材料，并配置题量、难度、题型、补充要求和模型。

前端先做最低限度检查：文字和文件不能同时为空；文件数量和大小必须在限制内。通过后创建 `analyze` 后台任务。

### 4.2 阶段二：材料分析（只分析，不出题）

系统把整理后的文字和图片发给模型，并明确要求：

- 只做材料结构与范围识别；
- 不设计蓝图；
- 不生成新题；
- 把材料拆成可以独立勾选的原题或知识单元；
- 即使只有一项，也必须返回一项；
- 输出合法 JSON。

模型需要返回两部分：

#### A. `source_scope`

表示可供用户选择的内容范围：

```json
{
  "mode": "single 或 question_set",
  "title": "材料标题",
  "questions": [
    {
      "source_question_id": "source_01",
      "number": "1",
      "title": "短标题",
      "stem_excerpt": "可辨认的内容摘要",
      "question_type": "原题题型或知识单元类型",
      "knowledge_points": ["知识点"]
    }
  ]
}
```

#### B. `source_analysis`

表示材料的总体理解：

- 学科 `subject`；
- 材料/题目类型 `question_type`；
- 知识点 `knowledge_points`；
- 能力点 `skills`；
- 材料本身的难度或认知层级 `difficulty`；
- 正确解题路径 `solution_strategy`；
- 常见错误 `common_errors`；
- 不确定内容 `uncertainties`。

如果模型没有返回可用范围项，程序会生成一个 `source_01` 兜底项，标题来自知识点名称、模型标题或“原题/知识材料”，摘要来自输入文本。

对应代码：`app/exercise_generation.py:591-667`。

### 4.3 阶段三：人工确认范围和出题方式

分析结果不会直接进入正式生题。页面会列出所有识别出的原题或知识单元，默认全选，让用户确认：

- 哪些内容参与出题；
- 采用哪种生成方式；
- 最终题量或每项变式数；
- 难度；
- 题型组合；
- 补充要求。

页面提供三种方式：

| 页面名称 | 内部值 | 用户含义 |
|---|---|---|
| 整体综合出题 | `targeted_set` | 综合所有选中内容，生成指定总题量 |
| 一一对应出题 | `parallel_exam` | 每个选中项目对应一道题 |
| 逐项出题 | `per_question` | 每个选中项目生成 1～3 道题 |

对应界面：`web/index.html:873-920`；确认逻辑：`web/app.js:1865-1974`。

### 4.4 阶段四：生成并人工审查蓝图

确认范围后创建 `plan` 任务。蓝图阶段仍然不生成具体题干，而是形成逐题设计表。

蓝图包括：

#### A. 整体训练目标

- `training_goal`：整套题要练成什么；
- `progression`：逐题梯度；
- `design_notes`：整体设计原则。

#### B. 每题计划 `exercise_plan`

每一题都包含：

| 字段 | 含义 |
|---|---|
| `number` | 题号 |
| `question_type` | 题型 |
| `difficulty` | 基础 / 进阶 / 挑战 |
| `target_skill` | 具体训练能力 |
| `variation_type` | 变式方式 |
| `design_intent` | 为什么这样设计 |
| `source_question_id` | 对应的原题或知识单元 |

前端允许人工逐题修改训练目标、题型、难度、目标能力、变化方式和设计意图。修改直接写回当前蓝图对象，最终生成时使用修改后的蓝图。

对应代码：`web/app.js:1977-2033`。

### 4.5 阶段五：按蓝图分批生成具体题目

用户确认蓝图后，创建 `generate_from_plan` 任务。

程序不会让模型一次生成全部题目，而是：

1. 读取蓝图的 `exercise_plan`；
2. 最多接受 30 项；
3. 每批最多 5 题；
4. 每一批都带上原始材料、材料分析、已选范围和本批蓝图；
5. 要求模型恰好生成本批规定数量；
6. 合并所有批次结果；
7. 由程序重新编号、规范字段并做质量检查。

分批的主要目的，是降低一次输出过长导致截断、漏题或 JSON 失败的概率。

对应代码：`app/exercise_generation.py:905-1022`。

### 4.6 阶段六：展示、修改、保存和导出

生成完成后，页面展示：

- 原材料分析；
- 训练目标；
- 每道题的题型、难度和知识点；
- 题干、选项和结构化题目资源；
- 公式、表格和图形；
- 结构质量检查结果。

用户后续可以：

- 手工编辑单题；
- 只重新生成某一道题；
- 收藏和筛选题目；
- 保存/覆盖历史记录；
- 导出“题目卷”Word；
- 复制纯文本。

## 5. 不同场景的具体逻辑

### 5.1 场景 A：按一道原题出题

识别结果只有一道题时，范围模式为 `single`。用户确认后可以按以下方式处理：

- **整体综合出题**：通常按指定总题量围绕这道题的考点做一组训练；
- **一一对应出题**：生成 1 道同结构平行题；
- **逐项出题**：为这道题生成 1～3 道变式。

如果没有传入已选来源，兼容逻辑最多接受 8 题，默认 5 题；题型从用户选中题型中轮换随机分配，未选则从 8 类允许题型中分配。

### 5.2 场景 B：按整套试卷/多道原题出题

分析阶段把试卷拆为多个 `source_question_id`。用户可取消不参与出题的题目，然后选择三种策略之一。

#### B1. 整套专项补强 `targeted_set`

- 总题量由 `strategy_count` 指定；
- 程序限制 1～20 题；
- 题目不要求平均分配到每道原题；
- 提示模型按选中原题的考点重要性组织训练；
- 蓝图可自行决定每题对应哪个来源，但必须在已选来源范围内。

适合：从一套题中抽取共性薄弱点，生成一套集中训练。

#### B2. 平行试卷 `parallel_exam`

- 每个选中原题对应一题；
- 最多读取前 30 道选中题；
- 程序继承每道原题的题型；
- 每题的 `source_question_id` 由程序固定，不交给模型自由改变。

适合：保持原卷结构，生成一套一一对应的新题。

#### B3. 逐题变式 `per_question`

- 每道选中原题生成 1～3 道变式；
- 总数最多 30 题；
- 如果用户指定了题型，程序按所选题型轮换分配；
- 未指定题型时继承对应原题题型；
- 来源 ID 由程序按原题展开并固定。

适合：针对每道错题分别做多个变式。

三种策略的后端计算：`app/exercise_generation.py:553-588`。

#### B4. 蓝图确认后的多题开关

这项能力与 `per_question` 不同：`per_question` 在范围阶段按来源复制蓝图项；蓝图多题开关则在用户审查完蓝图后，让每个已确认蓝图项派生 2～3 道子题。

- 关闭时仍严格执行“一项蓝图 → 一道题”，兼容既有任务与历史数据；
- 开启时可选择递进训练或同难度变式；
- 每道子题使用独立 `plan_item_id`，同时保留 `parent_plan_item_id`、变式序号和角色；
- 结果页按父蓝图标明“蓝图 X · 变式 Y/Z”，单题编辑、重生、选择和导出仍以子题唯一身份工作；
- 同组题由一个小批次生成，并检查去数字后的题干结构相似度；缺题仍按单题补生；
- 最终题量不设强制上限。超过 30 题时前端只提示生成时间、模型费用和配图处理量增加，不拦截提交、不截断题量。

### 5.3 场景 C：只有一个知识点名称

例如只输入“晶胞 / 点阵参数”。前端把它组合为：

```text
# 知识点名称

晶胞 / 点阵参数
```

系统仍会先分析知识边界，再设计蓝图。知识点模式没有原题，因此蓝图提示会要求：

- 明确核心概念和必要前置知识；
- 识别适合训练的关键能力；
- 不机械复述定义；
- 不假设存在一份原题；
- 在材料不足时把不确定处写入 `uncertainties`。

如果没有传入已经分析过的 `source_scope`，内部策略记为 `knowledge_targeted`。

### 5.4 场景 D：知识点名称 + 教材原文/资料

系统同时使用名称、粘贴文本以及上传文件解析出的文字和图片。分析阶段按章节、概念或能力单元拆分，让用户选择参与生成的知识单元。

确认后：

- 选择“整体综合出题”时，综合选中的知识单元形成一套题，内部记为 `knowledge_overall`；
- 选择“逐项出题”时，每个选中知识单元生成指定数量，内部记为 `knowledge_item_wise`；
- 每题仍由程序指定题型和难度，并可在蓝图页面人工修改。

当前实现中，知识点模式只有 `per_question` 被单独识别；其他页面策略值都会进入整体综合分支。因此页面上的“一一对应出题”在知识点后端并没有独立的 `knowledge_parallel` 语义，而会按整体题量逻辑处理。这是当前代码的实际行为，产品文案与后端语义需要注意保持一致。

对应代码：`app/exercise_generation.py:690-716`。

### 5.5 场景 E：包含图片的原题或知识材料

一旦解析结果中存在图片，分析、蓝图和正式生题都会走视觉服务商/视觉模型。发送给模型的用户内容由一个文本块和若干 `image_url` 块组成。

需要注意：

- 不再把模型阶段的 8 张质量建议当作硬上限；9～24 张已接收图片不会因此阻断或只保留前 8 张；
- 短材料把全部已接收图片放入同一次分析请求，保持跨图关系；长文本只按段落长度分段，并按 `IMAGE_REF` 把相关图片带入对应段；
- PDF 页面图和 DOCX 内嵌图共用 24 张材料接收边界，超过部分在逐文件诊断中列明；
- 图片顺序受用户上传顺序、PDF 页序和 DOCX 压缩包媒体文件名排序影响；
- 有图但服务商不支持视觉时会直接失败。

### 5.6 场景 F：单题重新生成

结果页点击“重新生成本题”时，不会重跑整套任务。系统只向模型提供：

- 当前整套的原材料分析；
- 当前蓝图；
- 当前这一题；
- 用户补充修改要求；
- 必须保持的题型和研究生层级。

模型只返回一题。程序随后保留原来的 `exercise_id`、题号和 `source_question_id`，并自动保存更新后的整套历史记录。

当前单题重生固定使用**文本模型**，不会重新附带原始图片；而且前端当前无论处于哪种模式，都取“按题出题”的文本模型配置，并未在知识点模式下切换到知识点专用模型。如果该题强依赖图片，或知识点模式使用了不同的专用模型，这是需要特别复核的边界。

对应代码：`app/exercise_generation.py:1025-1090`、`web/app.js:2231` 附近。

### 5.7 场景 G：旧接口一次性生题

后端仍保留 `/api/practice/generate` 和 `generate_practice_set()` 兼容入口。它会在一个请求内部先生成蓝图，再立即生成具体题目并保存。

当前主界面使用的是后台三段式任务，不依赖此兼容入口。兼容入口跳过了页面上的人工范围确认和蓝图审查，因此不应作为主要人工生产流程。

对应代码：`app/exercise_generation.py:1093-1096`、`app/server.py:730-745`。

## 6. 题量、题型和难度到底由谁决定

### 6.1 题量

| 场景 | 程序限制 |
|---|---|
| 单题/无已选来源的兼容分支 | 1～8，默认 5 |
| 整体综合出题 | 1～20，默认 10 |
| 平行试卷 | 选中来源数，最多 30 |
| 逐项变式 | 选中来源数 × 1～3，最多 30 |
| 知识点整体出题 | 1～20 |
| 正式按蓝图生成 | 取蓝图项数，最多 30 |

### 6.2 题型

允许的题型固定为：

```text
单选题、多选题、判断题、填空题、简答题、计算题、作图题、综合题
```

规则：

- 用户选了题型：程序随机打乱所选题型并循环铺满题量；
- 用户未选题型：程序从全部 8 类题型中随机铺排；
- 平行试卷：默认继承原题题型；
- 逐题变式：未手选题型时继承原题题型；
- 蓝图模型即使返回了别的题型，规范化阶段仍用程序计划覆盖；
- 人工在蓝图页面修改后，正式生题使用修改后的题型。

### 6.3 难度

程序先把难度模式转成逐题难度表，再覆盖模型返回值：

| 模式 | 5 题示例 |
|---|---|
| 基础 | 基础 × 5 |
| 进阶 | 进阶 × 5 |
| 挑战 | 挑战 × 5 |
| 基础为主 | 基础 × 4 + 进阶 × 1 |
| 基础到进阶 | 基础 × 3 + 进阶 × 2 |
| 进阶为主 | 进阶 × 4 + 挑战 × 1 |
| 同等难度 | 当前实现等同“全部进阶” |
| 进阶到挑战 | 进阶 × 3 + 挑战 × 2 |
| 其他/缺省 | 基础、进阶、挑战分段分配 |

蓝图页面人工修改难度后，最终生题使用人工修改值。

对应代码：`app/exercise_generation.py:125-134`、`491-508`、`553-588`。

## 7. 模型在三个阶段分别看到什么

### 7.1 分析阶段提示内容

模型会看到：

- 原题文字或知识材料文字；
- 当前分析段需要的全部已接收图片，整份材料最多保留 24 张；
- 模式说明（原题/知识材料）；
- 拆分范围的规则；
- `source_scope + source_analysis` JSON 结构。

模型不会看到蓝图，也被禁止生成新题。

温度：`0.1`。

### 7.2 蓝图阶段提示内容

模型会看到：

- 原始材料文字和图片；
- 知识点名称（知识点模式）；
- 用户补充要求；
- 题量、策略、题型计划、难度计划；
- 用户确认的原题/知识单元；
- 蓝图 JSON 契约。

模型被要求只做教学设计，不输出题干。

温度：`0.2`。

### 7.3 正式生题阶段提示内容

模型会看到：

- 原始材料文字和图片；
- 已确认的 `source_analysis`；
- 已确认的原题/知识范围；
- 人工最终确认的蓝图；
- 当前批次的 1～5 个逐题计划；
- 完整题目字段契约。

模型被要求：

- 恰好生成本批规定数量；
- 严格遵守逐题蓝图；
- 保持研究生层级；
- 条件充分、答案明确；
- 不能只替换数字；
- 公式进入 `formulas`；
- 表格进入 `tables`；
- 图形规格进入 `figures`；
- 只输出合法 JSON。

温度：`0.35`。

### 7.4 单题重生提示内容

只包含当前分析、整套蓝图、当前题和补充要求，不包含整套其他题正文，也不包含原始图片。

温度：`0.45`。

### 7.5 JSON 输出和自动修复

所有阶段通过 `chat_json()` 请求结构化 JSON，单次最大 token 至少 10000。

如果首次 JSON 解析失败，程序会再调用一次相同模型，要求只修复 JSON 语法，不改变内容，并关闭思考模式、温度设为 0。解析器还会：

- 去掉 `<think>...</think>`；
- 去掉 Markdown JSON 围栏；
- 尝试提取首个 `{` 到最后一个 `}`；
- 修复 LaTeX 反斜杠造成的非法 JSON 转义；
- 允许字符串中的控制字符。

两次都失败时任务失败，并把错误写入任务记录。

对应代码：`app/exercise_generation.py:136-203`、`368-409`。

## 8. 最终题目数据结构

正式结果的 schema 为 `answer_book.practice_set.v1`。

每道题包含：

| 字段 | 内容与程序处理 |
|---|---|
| `exercise_id` | 程序重新生成，如 `practice_01` |
| `number` | 程序按结果顺序重新编号 |
| `question_type` | 8 类允许题型之一 |
| `source_question_id` | 对应原题/知识单元 |
| `difficulty` | 基础 / 进阶 / 挑战 |
| `target_skill` | 目标能力 |
| `variation_type` | 变式方式 |
| `stem` | 完整独立题干 |
| `options` | 选项，最多 8 项，自动补 A/B/C… 标签 |
| `knowledge_points` | 知识点，最多 10 个 |
| `verification_note` | 模型的内容自检说明 |
| `formulas` | 最多 16 个公式对象 |
| `tables` | 最多 6 个表格对象 |
| `figures` | 最多 6 个图形规格 |

公式对象包含 LaTeX、题干/解析位置、行间显示和说明；表格包含表头与二维行数据；图形包含类型、标题、说明、坐标轴和数值序列。

页面能直接绘制带数值点的折线图、柱状图和散点图。没有数值序列的示意图只显示“图示规格说明”，并不是调用图片生成模型生成真实位图。

对应代码：`app/exercise_generation.py:29-123`、`206-294`、`297-340`；前端图形：`web/app.js:1080-1170` 附近。

## 9. 程序质量检查：做了什么、没做什么

### 9.1 已做的结构检查

程序会检查：

- `exercises` 必须是非空列表；
- 每题必须有非空题干；
- 结果题数是否等于请求题数；
- 选择题是否至少有 2 个有效选项；
- 知识点、蓝图项和来源覆盖是否可核对；
- 题型、难度是否属于允许值；
- 字段长度、数组数量是否超限；
- 题号、ID、计划题型和来源 ID由程序重建或覆盖。

检查结果写入：

```json
{
  "quality": {
    "status": "passed 或 warning",
    "warnings": [],
    "generated_count": 5
  }
}
```

### 9.2 重要区别：warning 不会阻止保存

少题、选择题选项不足、缺知识点或蓝图/来源覆盖不完整时记为 `warning`，仍保留部分结果，但整套正式导出暂停。只有没有任何可用题目、缺少蓝图、输入无效、模型失败或 JSON 无法修复等情况才会使任务失败。

### 9.3 当前没有自动完成的内容质量验证

当前结构检查不会真正证明：

- 题目在学科上正确；
- 题目中的计算数值经过独立复算；
- 题干条件一定充分；
- 新题与来源题没有过度重复；
- 题目确实达到研究生层级；
- 没有超出知识材料；
- `verification_note` 的自检结论真实可靠。

这些仍依赖模型自检和人工审查。`verification_note` 目前是模型输出文本，不是程序独立验证器的结果。

对应代码：`app/exercise_generation.py:206-294`。

## 10. 保存、任务状态和失败恢复

### 10.1 临时后台任务

每个 `analyze`、`plan`、`generate_from_plan` 都保存为：

```text
DATA_ROOT/practice_jobs/generation_*.json
```

记录中包含：任务类型、模式、标题、状态、阶段、完整请求、结果、历史 ID 和错误。

状态流：

```text
queued → running → completed
                  ↘ failed
```

服务重启时，遗留的 `queued/running` 会被标记为失败，错误为“服务重启导致任务中断，请重新发起”，不会自动从中间继续执行。

### 10.2 正式历史记录

只有 `generate_from_plan` 完成后才自动写入正式历史：

```text
DATA_ROOT/practice_history/practice_*.json
```

历史记录保存：

- 标题和时间；
- 输入文字摘要；
- 精简请求配置；
- 完整出题结果；
- 使用的模型信息。

为减少体积，历史记录的请求部分只保存上传文件名，不保存上传文件的 Base64 内容。因此从历史列表“复用”时，原上传文件正文/图片不能仅靠该精简请求完整恢复；历史结果本身仍可查看和编辑。

对应代码：`app/practice_store.py:31-90`。

### 10.3 任务中心展示

后台任务会出现在统一任务列表中：排队显示约 15%，运行中显示约 55%，完成/失败显示 100%。生成完成并已有正式历史 ID 后，临时任务从任务列表中过滤，避免与正式历史重复显示。

对应代码：`app/server.py:333-370`、`app/practice_jobs.py:81-97`。

## 13. 当前实现中值得重点关注的边界与风险

以下不是推测，而是从当前代码行为直接得出的维护注意点。

1. **按题和知识点仍使用不同蓝图契约。** 前者检查来源变式和结构变化，后者检查知识单元覆盖与教学梯度。
2. **结构检查不是学科正确性检查。** `passed` 的准确含义是结构、资源和范围检查通过，仍需教研复核。
3. **教材证据不足不会阻断用户。** 每个知识点会写入 `evidence_status=unavailable`，答案册中保留“未确认到可用教材依据”的标注。
4. **后台任务轮询默认只返回轻量状态。** 只有带 `?detail=1` 才读取 payload/result，避免 Base64 材料被重复传输。
5. **正式生成按 `plan_item_id` 合并。** 少题、多题或乱序不能静默串位；缺失项会保留失败占位并支持检查点重试。
6. **后台出题支持取消。** 取消后迟到的 Provider 响应不会把任务重新写成成功。
7. **图形主要是结构化图表，不是真实 AI 生图。** `figures` 有数值点时程序绘图，无数值点时以示意说明文字呈现。

## 15. 最终结论

当前生题系统的核心优点是：**用程序把模型限制在“分析、设计、生成”三个局部任务中，并在范围和蓝图两个关键节点引入人工确认。** 题量、题型、难度、来源 ID、题号和结果结构有较强的程序控制，不完全依赖模型自由发挥。

当前最需要人工把关的仍是：

- 学科正确性和题目数值复核；
- 是否超纲；
- 题干条件是否充分；
- 多批次之间是否重复；
- 有图题重生后的视觉一致性；
- `quality.warning` 中的少题、少选项、知识点或覆盖问题。

因此，这套流程目前更准确的定位是：**“可审查、可编辑、可追踪的模型辅助生题系统”**，而不是全自动无需复核的题库生产器。
