# 正式源码版本发布操作手册

本手册用于结束一个优化阶段并发布普通用户可更新的源码版本。发布者必须逐项执行，不得只推送 `main` 或只生成本地 ZIP。

## 1. 冻结与确认工作树

1. 停止所有并行审查、真实模型调用和新增改动，等待正在写入的任务安全收尾。
2. 确认只在最新发布工作树操作；旧版本目录只能用于差异取证。
3. 检查 `git status --short`、分支、远程地址和最近标签，确认所有待发布文件都属于本阶段。
4. `.artifacts/`、API Key、任务、教材、日志、输出、缓存和本机配置不得进入提交或源码包。
5. 未完成但尚未实现的事项写入交接或版本说明，不得在发布门禁期间顺手扩大改动。

## 2. 使用可复现的验证环境

- 官方源码发布工作流使用 Python 3.11，并按 `requirements.txt`、`requirements-dev.txt` 和 `constraints-py311.txt` 安装锁定依赖。本地发布验证应尽量使用同样的独立环境。
- 不要假定仓库 `.venv` 或应用运行时自带 `pytest`。先显式检查 Python 版本、pytest、Pydantic、python-docx、Ruff、Mypy 和 Coverage 是否来自同一兼容环境。
- 临时把一个环境的 `site-packages` 注入另一个 Python 只能用于诊断，不能作为“完整发布门禁通过”的证据；这种组合可能导致 TLS、进程锁、符号链接等测试产生环境性失败。
- Windows 无法创建符号链接、缺少 Node.js 或本地 TLS 测试服务异常时，要把环境性失败与代码回归分开：先单独复跑失败项并核对原因，再以官方 Python 3.11/Linux 发布工作流作最终裁决，禁止直接忽略失败。

## 3. 门禁与容易遗漏的测试契约

1. 先运行 `python scripts/run_quality_gates.py`；正式标签的 GitHub Actions 还会运行 `python scripts/run_quality_gates.py --full`。
2. 新增持久化任务字段或函数参数时，不仅要修改数据类和调用方，还要更新恢复路径、历史数据默认值以及 mock/精确字典断言。否则定向测试可能通过，整库恢复测试仍会失败。
3. 质量门禁中的文件路径必须统一为 POSIX 形式后再和排除清单比较；Windows 的反斜杠会让冻结发布脚本意外进入平台门禁。
4. 前端改动至少执行脚本语法检查、前端契约测试和真实浏览器关键流程；当前机器没有 Node.js 时必须记录这一限制，并依赖 CI 的 Chromium 门禁补足，不能声称本地已完成浏览器全验收。
5. 运行 `git diff --check`，并检查新文件是否已被测试和发布包纳入。

## 4. 版本元数据必须完全一致

正式版本使用新的补丁、次版本或主版本号，并同步：

- `APP_VERSION`
- `VERSION`
- `RELEASE_MANIFEST.json` 中的 `version`、`source_revision`、日期和真实验证记录
- `CHANGELOG.md` 中完全匹配的 `## [版本]` 条目

随后运行 `python scripts/check_version_consistency.py`。标签必须严格为 `v<APP_VERSION>`；`main` push 不会向普通用户发布更新。

## 5. 本地源码包与反向验证

1. 先把本版本新增源码和文档明确加入 Git 暂存区；本地打包器只读取 Git 索引中的文件，拒绝把任意未跟踪运行目录打进包。
2. 使用 `python scripts/package_release.py --output <明确路径>` 生成本地源码包。
3. 使用 `python scripts/verify_release_package.py <同一 ZIP>` 反向检查包内版本、清单、禁止文件和运行数据泄漏。
4. 从 ZIP 解压到临时目录，使用独立 `ANSWER_BOOK_DATA_DIR` 启动，确认 `/api/version` 返回新版本且首页可访问。
5. 本地包只是发布候选证据，不等于 GitHub 正式版本。

## 6. GitHub 发布顺序

1. 提交全部源码、测试、文档和版本元数据。
2. 推送当前分支到源码仓库，确认远程提交一致。
3. 创建并推送完全匹配的版本标签。
4. 观察 `.github/workflows/source-release.yml`：完整门禁、源码 ZIP 启动冒烟、公开 Release 和 `update-stable-v2.json` 必须全部成功。
5. 到公开更新仓库核对 Release 资产、SHA256/更新清单和版本说明；再从本地旧版执行一次“检查更新”，确认客户端能看到新版本。

桌面安装包属于手动兼容渠道，不得把桌面打包结果混同为源码更新版，也不得让它阻塞主源码发布。

## 7. 发布汇报必须区分状态

汇报时分别写明：

- 源码已修改
- 本地预览已验证
- Git 已提交并推送
- 本地源码 ZIP 已生成并反向验证
- GitHub Actions 是否成功
- 正式源码更新版是否已出现在公开下载源
- 桌面安装包是否另行发布

任何一步未完成都必须明确写“未完成”，不得用“已发布”概括多个不同状态。

## 8. 2026-08-27 发布收口经验

- 并行专项会共享同一工作树；发布前必须先冻结各专项，否则测试和版本文件可能在验证期间继续变化。
- 应用运行时没有 pytest，仓库 `.venv` 也未必包含开发工具；不要在门禁开始后才假设某个 Python 环境完整。
- Windows 下 `str(Path.relative_to(...))` 产生反斜杠，曾导致冻结的打包脚本未被门禁排除；文件清单已改为 `Path.as_posix()`，后续不得回退。
- 新增 `document_diagnostics` 持久化选项后，恢复行为本身正确，但旧的精确调用断言没有同步更新；发布前必须运行整库测试，而不能只相信新增用例。
- 本地打包器曾未整体排除 `.artifacts/`；反向验证即使随后报错，也不能撤销敏感文件已经被写入 ZIP 的事实。打包必须从文件选择阶段排除整个隔离审计目录，并用回归固定该约束。
- `build/ux-audit-*` 也曾包含隔离 Key 数据，因此仅增加一个目录黑名单仍不充分。本地源码包现只允许 Git 已跟踪或已暂存的文件进入，并继续保留运行目录黑名单作为第二道防线。
- Windows 调用 Node.js 契约测试时应设置 UTF-8 子进程环境（例如 `PYTHONUTF8=1`），否则中文测试数据可能被父进程按 GBK 解码并产生假失败。
- 真实模型成功只能证明连接和特定阶段，不等于三条业务线最终交付均已验证。版本清单必须准确区分连接测试、知识规划、最终答案和 Word/PDF 验收。
