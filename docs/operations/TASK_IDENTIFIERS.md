# 用户任务编号与排查映射

用户只看到完整 `RW-XXXX-XXXX-XXXX-XXXX` 任务编号；内部 task_id、job_id、run_id、history_id 继续用于原来的存储/API/恢复，不改名、不迁移文件。

编号由 `app.task_identity.public_task_number` 的固定 v1 算法确定。同一生题批次的阶段执行和历史结果共享编号；改标题、重试、更新源码不会改变编号。没有批次关联的历史独立任务保留各自编号，不能猜测并合并。算法及稳定键优先级属于兼容性合同，不得随意修改。

任务列表支持完整编号搜索和复制。`AB-...` 是提交反馈后返回的反馈单号，不是第二个任务编号；内部诊断追踪号保留在诊断数据，不在普通错误文案另行展示。

## 用户只提供任务编号时

在该任务数据所在电脑运行：

```sh
.venv/bin/python scripts/resolve_task_number.py RW-XXXX-XXXX-XXXX-XXXX
```

也可只读请求 `/api/tasks/resolve-number?number=RW-XXXX-XXXX-XXXX-XXXX`。返回全部关联执行和历史记录的内部标识，不返回原题、教材、密钥或模型输入。查找不受最近 100 项列表上限影响，不会自动选中或修改任务；没有匹配明确返回 found=false。多个匹配是同批次历史执行，需根据反馈时间和执行状态进一步定位，不能盲选首条；极端哈希冲突同样不得盲选。

任务卡片的反馈上下文同时携带 public_task_id、stable_task_id、实际 job_id 和 history_id。生题执行反馈必须以真实 job_id 采集生命周期和调用记录，不能用稳定批次编号代替。诊断包 manifest 保留用户编号和内部稳定标识。

任务已删除且诊断包也未保留时，仅凭编号不能恢复不存在的数据。跨电脑排查需该电脑的反馈包/数据；编号不是云端同步机制或访问令牌。
