# 运行健康监测优化任务说明

## 项目范围

`/Users/ljj/Documents/分析多模态问题/answer_book_platform_v1_v6.8_material_figure_schema_flow_standalone`

## 任务目标

在现有运行监控、任务进度、日志和局部心跳基础上，补齐服务、任务和模型调用的轻量健康监测，使用户能够判断程序是在正常运行、等待模型、响应较慢、可能卡住还是已经失败。

本任务不建设复杂运维平台，不引入外部监控服务，不定时调用收费模型做健康探测，也不改变解析和生题的业务流程。

## 一、统一健康状态

后端统一输出以下四种用户状态，前端不要直接展示内部错误码：

- `normal`：运行正常，任务持续有进展；
- `waiting`：任务仍在运行，正在排队、等待模型或处理耗时内容；
- `warning`：长时间没有新的业务进展，可能响应较慢或卡住，需要关注；
- `error`：服务、模型调用或任务已经明确失败。

同时保留 `unknown` 表示尚无足够运行记录，不能把“没有调用过”显示为异常。

健康状态必须区分两个时间：

- `last_heartbeat_at`：后台工作线程是否仍存活；
- `last_progress_at`：最近一次真正完成题目、图件、批次或阶段的时间。

仅有心跳但长期没有业务进展时，应显示“仍在运行，但等待时间较长”，不能一直显示“正常”，也不能未经判断直接宣布任务失败。

## 二、后端监测要求

### 1. 服务健康

扩展现有 `app/runtime_monitor.py` 和 `/api/system/status`：

- `ok` 不再固定为 `true`，根据实际状态生成总体健康结论；
- 返回服务启动时间、运行时长、当前进程、数据目录是否可写、任务目录是否可写、剩余磁盘空间；
- 汇总正常、等待、疑似停滞和失败任务数量；
- 汇总当前模型请求数、等待请求数、近期成功数、失败数、超时数和重试数；
- 任一监测项读取失败时记录该项异常，不得导致整个状态接口失败。

不强制新增第三方系统资源依赖。CPU、内存如果能通过现有环境稳定读取可以展示，否则本次以影响任务能否继续执行的进程、目录写入和磁盘空间为主。

### 2. 解析与生题任务健康

为解析主流程和生题后台任务统一记录：

```json
{
  "health_status": "normal|waiting|warning|error|unknown",
  "current_operation": "正在理解题面",
  "completed_count": 3,
  "total_count": 8,
  "last_heartbeat_at": "...",
  "last_progress_at": "...",
  "active_item": "第4题",
  "active_since": "...",
  "warning_reason": "",
  "suggested_action": ""
}
```

要求：

1. 解析主流程从任务启动到结束均有统一心跳，不只覆盖图件阶段。
2. 题面理解、知识规划、证据选择、答案生成、作图、质量回修和正式生题等可计数阶段，应更新完成数、总数和 `last_progress_at`。
3. 单次模型请求开始时记录当前操作、题号或图号及开始时间；结束后记录成功、失败或超时。
4. 等待人工确认时显示“等待用户确认”，不得判定为停滞。
5. 等待并发执行槽时显示“正在排队”，不得判定为卡住。
6. 任务失败、取消、完成后必须停止心跳，并写入最终状态。
7. 服务重启后，沿用现有恢复规则；不能恢复的解析任务明确显示“服务重启导致任务中断”，可恢复的生题任务显示“正在恢复任务”。

### 3. 停滞判断

停滞判断应使用可配置阈值，并结合当前操作的请求超时，不使用一个固定分钟数覆盖所有阶段：

- 心跳正常，且仍处于单次模型允许等待时间内：`waiting`；
- 心跳正常，但超过当前操作的合理等待或超时范围仍无进展：`warning`；
- 心跳也已超过允许间隔，或任务线程明确异常退出：`error`；
- 用户确认、并发排队、模型重试均有独立状态，不按普通停滞处理。

`warning` 只用于提示和提供重试入口，不自动终止任务。明确到达现有任务或模型超时后，继续执行原有失败和降级规则。

### 4. 模型调用监测

在公共模型调用层统一记录，不在每个业务模块重复实现。每次实际请求至少记录：

- 所属任务、阶段、题号/图号或批次；
- 模型用途、供应商和模型名；
- 排队时间、请求开始与结束时间、总耗时；
- 成功、失败、超时、限流、重试及降级结果；
- 当前并发数和配置并发上限。

监测记录不得保存 API Key、完整提示词、完整题面、模型原始回答或用户上传材料。错误内容应截断并脱敏。

供应商健康根据真实业务调用被动计算：

- 最近调用正常：显示“最近调用正常”；
- 响应耗时明显增长：显示“近期响应较慢”；
- 连续出现超时、限流或失败：显示“近期调用不稳定”；
- 尚未发生调用：显示“暂无调用记录”。

不得通过定时发送模型请求维持“在线”状态，现有手动 API 测试继续保留。

### 5. 并发运行监测

配合并发优化，按阶段展示：

- 待处理数量；
- 正在处理数量；
- 已完成数量；
- 失败数量；
- 当前并发数/并发上限。

结果汇总仍按题号、图号或蓝图顺序展示，不能让并发完成顺序影响用户看到的顺序。

## 三、前端展示要求

### 1. 运行监控页

保留现有“运行监控”页面并改造成普通用户可直接判断的总览：

- 页面顶部显示总体结论：
  - “系统运行正常”；
  - “有任务等待时间较长”；
  - “部分模型调用不稳定”；
  - “系统存在需要处理的问题”。
- 显示服务运行时长、当前任务数、正在处理数、等待数、疑似停滞数和失败数。
- 增加“模型调用状态”区域，以“最近调用正常、响应较慢、近期不稳定、暂无记录”展示，不默认暴露 HTTP 状态码等技术信息。
- 增加“正在运行的任务”区域，展示任务名称、当前正在做什么、完成数量、已用时间和最后一次进展时间。
- 增加磁盘空间和目录写入异常提示；正常时不占用过多页面空间。
- 页面可见时每 5 秒左右自动刷新；页面隐藏后停止刷新，保留手动刷新按钮。

### 2. 任务列表

每个运行中任务卡片增加简洁状态，不把用户逼到监控页才能判断：

- “运行正常 · 已完成 3/8 题”；
- “正在等待模型返回 · 已等待 42 秒”；
- “正在排队 · 前面还有任务处理中”；
- “等待时间较长 · 建议继续等待或查看详情”；
- “任务已中断 · 可重新运行”。

普通状态只显示一句话；出现 `warning` 或 `error` 时才突出颜色和操作按钮。

### 3. 任务详情/进度页

任务详情中展示：

- 当前阶段和正在处理的题目、图件或批次；
- 已完成数量/总数量；
- 当前阶段已用时间；
- 最近一次实际进展；
- 并发阶段显示“同时处理 2/3 项”，不使用“线程池、worker”等开发术语；
- 等待较长时给出可执行建议，如“继续等待”“取消任务”“重新运行”“检查 API 配置”。

“技术详情”放在可展开区域，供排查时查看供应商、模型、重试次数、超时、错误类别和最近日志；默认界面优先展示用户能理解的原因和建议。

### 4. 文案与颜色

- 正常：绿色或中性色，文案为“运行正常”“仍在继续处理”；
- 等待：蓝色，文案为“正在等待模型返回”“正在排队”；
- 警告：黄色，文案为“等待时间较长”“近期响应较慢”；
- 错误：红色，文案为“任务已中断”“模型调用失败”；
- 未知：灰色，文案为“暂无运行记录”。

不得把“等待模型返回”和“程序卡死”混为一谈；未经超时或心跳判断，不显示“卡死”。

## 四、实现边界

1. 复用现有 `runtime_monitor.py`、任务进度 JSON、运行日志、任务状态接口和前端监控页，不另建独立监控系统。
2. 使用公共监测结构和公共模型调用记录能力，避免各阶段自行定义不一致字段。
3. 健康监测只观察和提示，不改变题目分析、蓝图、答案、生题、作图和质量校验语义。
4. 不因为增加监测而把完整请求或响应重复落盘，避免隐私风险和明显磁盘膨胀。
5. 监测写入失败不能阻断主业务；记录失败后主任务仍按原流程执行。
6. 不做短信、邮件、第三方告警、自动重启和自动提高并发数。

## 五、建议实施顺序

1. 统一健康字段、解析主任务心跳和 `last_progress_at`。
2. 在公共模型调用层补充调用耗时、重试、超时、限流和并发记录。
3. 扩展 `/api/system/status`，形成服务、任务、模型三层健康汇总。
4. 改造运行监控页、任务列表和任务详情的普通用户展示。
5. 与并发优化一起验证排队、并行、部分失败、停滞和恢复场景。

## 六、验收要求

- 服务正常且任务持续推进时，监控页显示“系统运行正常”，任务完成数量持续更新。
- 单次模型调用仍在允许等待时间内时，显示“正在等待模型返回”，不误报失败或卡死。
- 心跳存在但长时间无实际进展时，显示“等待时间较长”，并提供查看详情、继续等待或取消等建议。
- 心跳停止或线程明确失败时，显示任务已中断及可执行的恢复建议。
- 等待用户确认和等待并发执行槽不会被误判为停滞。
- 并发处理时能够看到待处理、处理中、已完成和失败数量，题目与图件顺序不发生错位。
- 模型超时、重试、限流和降级能在技术详情中追踪，同时普通页面使用易懂文案。
- 运行监控页在可见时自动刷新，切到其它页面后不继续产生无意义请求。
- 服务状态接口能识别任务异常、目录不可写和磁盘空间不足，不再始终返回 `ok: true`。
- 监测日志不包含 API Key、完整提示词、完整模型回答或用户原始材料。
- 监测模块异常不会导致解析或生题任务失败。
- 补充服务健康汇总、任务停滞判断、模型调用记录、并发计数、前端状态映射和自动刷新测试。
- 完成后说明修改文件、状态判断规则、前端展示位置、监测写入内容以及测试结果。
