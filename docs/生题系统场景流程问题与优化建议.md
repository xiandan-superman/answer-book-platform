# 生题系统场景流程问题与优化建议（最终审查归并版）

> 审查日期：2026-08-01  
> 审查范围：按题出题、知识点出题、多文件/图片材料、范围确认、蓝图审查、分批生成、结果编辑、历史复用、失败恢复与导出。  
> 审查方法：以当前前端和后端代码实际行为为准，从真实使用者能否理解、校正、验收和恢复四个角度检查。

## 1. 审查结论

当前系统的主干方向是正确的：

```text
材料分析 → 人工确认范围 → 人工审查蓝图 → 按蓝图生成 → 结果编辑/导出
```

相比“一次性让模型直接出题”，它已经具备更好的可控性。但从使用者角度，仍有四类关键断点：

1. **系统理解是否正确，用户不容易判断和纠正。**
2. **界面承诺、用户配置与后端实际执行存在少数语义偏差。**
3. **生成后显示的“通过”不足以证明题目可用，编辑后质量状态还可能失真。**
4. **文件、任务和中间结果的恢复能力不足，失败后容易重复等待、重复付费或丢失上下文。**

建议优先完成 P0 的 7 项防错修复，再做 P1 的可审查、可恢复和质量门禁，最后处理 P2 的效率与体验问题。

## 2. 对初审清单的交叉审查

初审提出的 16 项问题方向基本成立。最终审查补充以下边界修正：

### 2.1 “历史复用丢失上传材料”需要分两种情况理解

- **原任务只有上传文件、没有粘贴文字**：历史复用不会静默生成，前端通常会因为文字和文件都为空而阻止下一步；但用户只看到“已复用历史记录”，随后才发现无法继续。
- **原任务同时有粘贴文字和上传文件**：复用后只剩粘贴文字，上传文件内容丢失，用户可能在不明显知情的情况下继续生成不完整结果。

所以核心问题仍然成立，但准确表述应是：**历史复用不能完整恢复材料，纯文件任务被阻断，混合材料任务可能降级后继续。**

### 2.2 “服务重启不可恢复”不仅是运行中任务

运行中的任务会被标记失败；此外，分析结果和未正式生成的蓝图虽然可能仍存在临时任务 JSON 中，但没有稳定的用户可见“阶段历史”和继续入口。即使阶段已经完成，刷新或离开后也难以可靠回到待确认状态。

### 2.3 “图题不完整”分网页与 Word 两条链路

- 有数值序列的折线/柱状/散点图，网页和 Word 都能程序绘制；
- 没有数值序列的 `diagram` 主要是文字说明，而非正式题图；
- 网页预览另有一个图形 ID 冲突问题，可能显示错图，见 P0-6。

### 2.4 补充发现 6 个初审未单列的实质问题

1. “同等难度”当前固定变成“全部进阶”，并不继承原题难度；
2. 某一生成批次少题/多题时，后续题可能与蓝图题型、来源 ID 错位；
3. 手工编辑后不重新校验，旧的 `quality=passed` 可能继续显示；
4. 多题图形使用重复 `figure_id` 时，网页可能把前题图显示成后题图；
5. 后台轮询每次返回完整 payload/result，含大文件 Base64，造成重复传输；
6. 蓝图界面显示的某些兜底文案并未真正写入蓝图数据，存在“看起来有值、实际为空”。

## 3. P0：会误导用户、错配结果或丢失工作成果

## P0-1 知识点出题策略的界面语义与后端行为不一致

### 当前行为

知识点模式和按题模式共用三种页面选项：整体综合、一一对应、逐项出题。但知识点后端只单独识别 `per_question`：

- `per_question` → `knowledge_item_wise`；
- 其他值（包括 `parallel_exam`）→ 整体综合逻辑。

因此用户选择“一一对应出题”，并不能保证每个知识单元对应一题。

### 用户影响

用户看到的是确定性承诺，实际得到的却是另一种分配策略。结果即使内容不错，也不符合用户明确选择。

### 优化建议

知识点模式使用独立策略：

- 综合覆盖：综合全部选中知识单元，指定总题量；
- 单元一一对应：每个知识单元恰好一题；
- 单元逐项扩展：每单元 1～N 题；
- 按权重分配：用户为单元设置权重或题量。

后端为每种策略建立显式枚举和独立计算，不再用“非 per_question 都归整体”的兜底。

### 验收标准

- 页面选项、请求值、蓝图 `generation_strategy` 和最终 `exercise_groups` 四处一致；
- 确认页显示每个知识单元的预计题数；
- 自动化测试覆盖 1、2、多个知识单元的所有策略。

代码证据：`app/exercise_generation.py:690-716`，`web/index.html:873-899`。

## P0-2 “同等难度”实际被固定为全部“进阶”

### 当前行为

`_difficulty_plan()` 把 `同等难度` 与 `进阶为主` 放在同一个分支；其中 `同等难度` 的题目全部被分配为“进阶”。程序没有读取原题难度作为基准。

### 用户影响

用户选择“同等难度”通常理解为“与原题难度相当”，但系统实际含义是“全部进阶”。基础题和挑战题都会被错误映射。

### 优化建议

- 分析阶段生成标准化 `source_difficulty`；
- “同等难度”按来源题逐题继承或按已选来源的分布复制；
- 如果难度判断不确定，界面明确要求用户确认，不默认进阶。

### 验收标准

- 基础、进阶、挑战来源题选择“同等难度”后分别保持对应层级；
- 多来源模式显示继承后的逐题难度分布。

代码证据：`app/exercise_generation.py:491-508`。

## P0-3 分批少题/多题会造成后续题与蓝图错位

### 当前行为

正式生成每 5 题一批。程序把各批返回的题目直接顺序合并，最后再按照全局序号覆盖题型和来源 ID。每个批次没有先验证“恰好返回本批题数”。

例如第一批应生成 5 题却只返回 4 题，第二批的第一题会成为合并列表第 5 题，从而被错误套用第一批第 5 项的题型和来源 ID。系统只提示总数不足，不会识别语义错位。

### 用户影响

题干可能来自知识单元 B，但界面和导出把它标成知识单元 A；平行试卷和逐题变式的来源关系会失真。

### 优化建议

- 每批结果按蓝图项的稳定 `plan_item_id` 对齐，禁止靠数组位置关联；
- 每批生成后立即校验数量、ID 和类型；
- 少题时只补生成缺失 ID，多题时拒绝或显式裁剪该批，不影响后续批次；
- 合并前验证所有计划 ID 恰好出现一次。

### 验收标准

- 模拟任意批次少 1 题、多 1 题、乱序返回时，来源和题型仍不串位；
- 缺失项被单独补齐或任务明确失败，不能只发 warning 后保存。

代码证据：`app/exercise_generation.py:927-993`。

## P0-4 历史复用无法完整恢复上传材料

### 当前行为

正式历史的精简请求只保存上传文件名，不保存文件内容、解析文本或图片引用；前端复用时却尝试读取 `request.source_files`。

### 用户影响

- 纯文件任务：复用后无法继续，需要重新上传；
- 混合任务：可能只用剩余文字继续，材料悄然不完整；
- 用户无法确认本次复用是否仍使用了原 PDF、Word 或图片。

### 优化建议

保存版本化“来源快照”：

- 提取后的文本块；
- 文件哈希、文件名和解析器版本；
- 页码/图片引用；
- 必要时保存受控副本，或要求重新上传并校验哈希。

如果完整材料不可用，复用入口必须明确提示并阻止继续，不能只显示“已复用”。

### 验收标准

- 纯图片、纯 PDF、混合资料三类历史均可准确重放；
- 无法重放时列出具体缺失文件，并提供逐个重新上传入口。

代码证据：`app/practice_store.py:58-90`，`web/app.js:1543-1558`。

## P0-5 单题重新生成丢失原始上下文并使用错误模型配置

### 当前行为

单题重生只传材料分析、蓝图、当前题和补充要求，不传原始文字或图片。前端无论按题还是知识点模式，都固定使用“按题出题”的文本模型配置。

### 用户影响

- 有图题失去读图上下文；
- 教材细节无法重新核对；
- 知识点任务可能换成不同服务商/模型；
- 用户以为只是“换一种变式”，实际生成条件已经改变。

### 优化建议

- 单题重生携带该题的来源快照、必要图页和 `source_mode`；
- 根据模式选择对应文本/视觉模型；
- 结果记录本次重生的模型、来源版本和调整要求；
- 若来源不可用，阻止重生并说明缺什么。

### 验收标准

- 知识点任务使用知识点模型配置；
- 有图题重生请求中包含正确图页；
- 重生前后可查看模型和来源差异。

代码证据：`app/exercise_generation.py:1025-1090`，`web/app.js:2231-2259`。

## P0-6 多道题的图形 ID 冲突会导致网页显示错图

### 当前行为

每道题的图形默认都可能命名为 `g1`。网页把整套题的所有图形放入一个以 `figure_id` 为唯一键的 Map；后面的 `g1` 会覆盖前面的 `g1`。多个 canvas 随后可能都读取最后一道题的图形数据。

### 用户影响

网页审题时题干和图不一致；用户可能依据错误预览做判断。Word 导出按题处理，不一定同样出错，于是网页与导出还可能不一致。

### 优化建议

- 使用 `exercise_id + figure_id` 作为全局唯一键；
- 规范化阶段为所有结构化资源生成全局唯一 ID；
- 增加网页预览与 Word 导出的逐题图形一致性测试。

### 验收标准

- 两题都含 `g1` 时，各自只显示自己的图；
- 网页和 Word 的题号、图题、数据序列一致。

代码证据：`app/exercise_generation.py:91-123`，`web/app.js:1152-1155`。

## P0-7 手工编辑后质量状态不重新计算

### 当前行为

用户可直接编辑题干、选项、答案、解析、公式、表格和图形。保存时只是修改当前对象并写回历史，没有重新调用规范化或质量检查；整套原来的 `quality.status` 和 warnings 仍然保留。

用户甚至可以清空答案、删成只有一个选项，页面仍可能继续显示旧的“结构检查通过”。单题重生替换后也没有重新计算整套质量状态。

### 用户影响

“通过”徽标失去可信度，人工修改可能把原本合格的题改坏后直接导出。

### 优化建议

- 编辑器保存前做字段级校验；
- 保存后重跑整套结构审计并刷新质量状态；
- 将模型生成质量和人工编辑后质量分开记录；
- 不合格时允许保存草稿，但禁止标记为可交付。

### 验收标准

- 清空答案、删除选择题选项、写入非法表格/图形时立即出现对应错误；
- 编辑后 `quality` 的时间和版本更新；
- 导出前再次校验，不能沿用旧通过状态。

代码证据：`web/app.js:2197-2224`，`app/exercise_generation.py:206-294`。

## 4. P1：用户无法充分校正、验收或恢复

## P1-1 范围只能勾选，不能编辑、合并或拆分

用户无法校正标题、摘要、知识点和边界，也不能手工新增遗漏单元。模型拆错后只能整体重跑。

建议：提供编辑、合并、拆分、新增、删除和“只重新分析本项”；所有人工改动进入来源快照并带版本。

## P1-2 缺少原文对照、页码、图片缩略图和不确定性提示

范围页只显示模型摘要，用户不能直接核对它来自哪一页、哪段或哪张图，也不容易看到 `uncertainties`。

建议：每个来源单元绑定 `file_id/page/block/image_id`，可展开原文与缩略图；截断、解析失败和不确定项使用醒目风险标记。

## P1-3 多文件和图文材料会无提示截断视觉内容

PDF 只转前 8 页图，DOCX 只取前 8 张内嵌图，所有图片汇总后再截到 8 张。用户不知道哪些页/图未送入模型。

建议：上传后展示逐文件解析清单、总页数、已用页、未用页和原因；允许选页、分批分析和继续追加。DOCX 图片还应保留与段落/表格的相对位置，而不是只按媒体文件名排序。

代码证据：`app/practice_inputs.py:41-107, 123-158`。

## P1-4 缺少课程和受众画像

当前大多依靠“研究生层级”和一段 `focus`，无法结构化设置课程方向、前置知识、目标年级、考试时长、分值、开放性、超纲边界等。

建议：增加可选教学画像并写入蓝图；将课程约束变为可验收字段，而不是全靠自然语言提示。

## P1-5 蓝图控制维度不足且存在“视觉兜底值”

用户不能增删、排序题目，不能调整知识单元关联和题量分配，也没有覆盖矩阵。另一个细节是：模型若未返回 `target_skill`，界面会显示“核心能力”作为输入框值，但该兜底值没有立即写回蓝图对象；用户不触碰输入框就确认时，后端收到的仍可能是空值。

建议：蓝图采用稳定计划项 ID；支持增删排序、来源关联、覆盖矩阵和题量分配；所有界面默认值在渲染时同步到数据层。

代码证据：`web/app.js:1977-2030`。

## P1-6 蓝图确认前没有真正的验收门槛

当前缺少知识点覆盖、来源覆盖、题型/难度分布、预计时长、重复计划和风险项检查。

建议：确认按钮前展示蓝图审计摘要；P0/P1 风险未解决时阻止生成或要求有记录的人工豁免。

## P1-7 结果质量检查过于基础

当前主要检查题数、选择题选项数和解析步骤，不能验证答案唯一性、选项对应、数值复算、知识点一致性、难度、重复度和公式/图表可渲染性。

建议分三层：

1. 结构审计：字段、选项、资源、渲染；
2. 正确性审计：答案、计算复算、选项唯一性；
3. 教学一致性审计：来源、知识点、难度、蓝图覆盖和重复度。

每题显示独立风险，不再用一个“passed”概括整套可用性。

## P1-8 图题交付链路不完整

`diagram` 可能只有文字规格；“选择作图题”不等于得到正式题图。建议在蓝图阶段声明需要的图形类型、生成方式和验收标准；结果阶段必须提供可视预览，并校验网页与 Word 一致。

## P1-9 编辑和重生没有版本、差异或撤销

修改后直接覆盖同一历史记录。建议采用“草稿 → 审计 → 保存版本”，支持前后差异、恢复旧版和另存分支。

## P1-10 任务没有取消、断点续跑和阶段历史

服务重启把运行中任务标失败，用户不能从已完成的分析或蓝图继续；长任务也没有取消入口。

建议：阶段产物独立持久化；任务幂等；支持取消、重试当前阶段、切换模型后继续、从蓝图继续。已完成的范围和蓝图应进入可见历史，而不是只依赖浏览器内存或临时 job。

## P1-11 失败提示缺少可执行恢复动作

建议按错误类型提供：重试、换模型、缩小材料、选择页码、修复 JSON、保留已完成阶段、查看诊断编号。不要只返回底层异常文本。

## P1-12 缺少并发与重复提交保护

每次请求都会创建新的后台线程；多窗口、多用户或重复点击可能并行执行相同高成本任务。建议增加任务指纹、幂等键、并发上限、排队策略和取消按钮。

## 5. P2：效率、成本与可理解性问题

## P2-1 同一材料在三个阶段被重复解析和发送

分析、蓝图、生成都会重新解析文件；正式生成还会每 5 题把整份材料再次发给模型。

建议：第一阶段生成版本化来源快照；后续按来源 ID 引用必要片段和图页，只在需要时追加上下文。

## P2-2 后台轮询重复返回完整大 payload/result

前端约每 1.2 秒读取 job；后端默认返回完整 payload 和 result。payload 可能包含多个文件的 Base64，导致生成期间反复传输大对象。

建议：轮询接口默认只返回状态、阶段、进度和错误；任务完成后再单独获取结果。文件内容使用服务器端引用，不放入反复轮询的 JSON。

代码证据：`web/app.js:802-830`，`app/server.py:592-594`，`app/practice_jobs.py:60-69`。

## P2-3 临时任务长期保留完整材料，存在存储与隐私负担

完成后的 job 文件仍可包含完整 Base64 上传内容和结果，即使任务列表已隐藏它。建议定义清理周期、最小化字段、材料加密/权限和用户可见的数据保留策略。

## P2-4 复制纯文本会遗漏结构化公式、表格和图形

纯文本复制只拼接题干、选项、答案和解析步骤，单独存放在 `formulas/tables/figures` 的内容不会完整进入复制结果。依赖结构化资源的题可能被复制成不完整题目。

建议：复制时按 location 把公式、表格和图示说明插回题干/解析；提供 Markdown、纯文本和完整 JSON 三种复制格式。

代码证据：`web/app.js:1041-1055`。

## P2-5 知识点任务仍使用“专项练习”导出文件名

两种模式导出都叫“专项练习-题目/答案与解析.docx”。建议根据 `source_mode` 使用“知识点模拟题”或“按题专项练习”，并在文档元数据中写入来源类型、蓝图版本和生成时间。

代码证据：`app/server.py:785-793`，`web/app.js:2290`。

## P2-6 用户可见阶段名称与真实模型调用次数不够透明

界面强调“两阶段生成”，实际主流程包含材料分析、蓝图、正式生成三个独立后台任务。建议明确“分析不出题、蓝图不出题、确认后才生题”，同时展示每阶段是否会调用模型、预计耗时和能否复用已有结果。

## 6. 建议实施顺序

### 第一批：先防止错误结果和成果丢失

1. 修正知识点策略语义；
2. 修正“同等难度”；
3. 为蓝图项增加稳定 ID，修复跨批错位；
4. 修复历史材料快照和复用提示；
5. 修复单题重生上下文/模型；
6. 修复图形 ID 冲突；
7. 编辑和导出前强制重算质量。

### 第二批：让用户真正能审查和控制

1. 范围可编辑、合并、拆分；
2. 原文/页码/图片溯源；
3. 蓝图覆盖矩阵和增删排序；
4. 蓝图确认前门禁；
5. 三层结果审计；
6. 版本、差异和撤销。

### 第三批：恢复、效率和成本

1. 来源快照复用；
2. 阶段检查点、取消和续跑；
3. 轻量轮询；
4. 并发与幂等；
5. 数据保留和清理；
6. 完整复制和模式化导出命名。

---

## 7. 推荐的验收主线

优化不应只按功能点验收，建议用以下端到端场景回归：

1. **纯文字单题**：同等难度、逐题 3 变式、编辑后导出；
2. **20 道试卷 PDF**：选页、选题、平行试卷、模拟某批少题后补齐；
3. **纯图片题**：视觉分析、范围溯源、单题重生仍带原图；
4. **知识点名称**：单题和多题难度、知识点专用模型；
5. **教材 PDF + DOCX + 图片**：截断提示、知识单元合并/拆分、历史复用；
6. **多题多图**：网页与 Word 的每题图形一致；
7. **人工编辑破坏结构**：质量状态立即变为不合格，导出被拦截；
8. **服务重启/网络超时**：从已完成阶段继续，不重复前序模型调用；
9. **两个浏览器重复提交**：幂等或明确排队，不重复付费；
10. **历史重放**：输入快照、蓝图、模型、版本和导出结果可追溯。

## 8. 最终判断

当前系统已经具备“可审查生题”的基本骨架，但真正影响使用者信任的不是再增加一种题型，而是做到：

- **看得见系统用了什么材料；**
- **改得了系统理解错的地方；**
- **确认的配置与实际执行完全一致；**
- **生成后的通过状态真实、可复核；**
- **失败或刷新后不丢已完成工作；**
- **历史任务可以完整、可追溯地复用。**

完成 P0 后，系统才具备稳定内部试用的基础；完成 P1 后，才更接近可持续用于正式题目生产的工作台。
