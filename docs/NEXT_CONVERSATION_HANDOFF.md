## 2. 优化的出发点

项目不是材料学专用程序。材料科学和物理化学文件只是当前真实测试样本，目标是形成跨学科、可扩展的真题解析与生题平台，而不是把主流程补成样题规则集合。

考虑 GitHub 或其他成熟项目，不是为了追求新技术，也不是整体替换现有程序，而是让成熟组件承担通用、确定性的基础能力：

- 文档、图片和公式解析；
- LaTeX、MathML、Word OMML 转换；
- 单位、上下标和专业符号的结构保留；
- 可参数化曲线、流程图和结构图的确定性绘制；
- PDF/DOCX 渲染、视觉检查和失败诊断；
- 任务队列、断点恢复、日志和运行监控。

本系统继续负责题目结构、教材证据绑定、答案组织、生题逻辑、跨学科能力调度、最终 Word 交付和质量治理。模型负责无法完全确定化的内容生成。

## 3. 必须保持的产品边界

1. 测试用于发现通用缺陷，不得为某道题、某个材料样本或某次模型输出增加特例。
2. 模型知识波动无法由程序彻底消除；程序必须保证模型正确内容不被结构、公式、图片、组装和渲染破坏。
3. 漏题、错序、空父级、题答错配、公式损坏、图片错位、最终答案与计算步骤矛盾属于程序责任。
4. 确定性检查优先；启发式或模型判断不得无限重试，也不得自动升级为硬门禁。
5. 原有题型内容、编号、字体、字号、段落和 Word 模板是产品契约，不能在重构中隐式改变。
6. 学科专用库只能作为可选能力包，不能进入所有学科默认主链路。
7. 新成熟组件必须通过真实文件 A/B，明确替换模块、开关、性能、维护成本和失败降级后才能引入。

## 4. 已实现的整体优化

### 4.1 跨学科能力架构

- `app/capabilities/` 统一声明 capability manifest、schema、renderer、validator、policy hook 和冲突检查。
- 通用核心只保留跨学科、低争议能力；材料规则迁入 `app/capabilities/builtin/materials.py`。
- 检索、公式审计、文本规范化、题目抽取和答案生成不再直接包含材料样题触发词。
- 旧专业图注册表只作兼容门面；新学科通过可选能力包扩展。

### 4.2 DOCX、公式和图片输入

- `app/practice_inputs.py` 和 `app/exam_extract.py` 按 `document.xml` 中真实顺序遍历段落和表格，避免表格统一移到文末。
- 新增 `app/omml_input.py`，使用 Microsoft Word 的 `omml2mathml.xsl` 保留 OMML 公式结构。
- 转换器不可用时保留可见字符并记录明确降级，不静默丢公式。
- Word 内嵌图保留 `IMAGE_REF` 正文位置，引用号与传给视觉模型的图片顺序一致。
- 图片使用统一全局上限；超过上限明确告警。
- DOCX ZIP 中的 `word/media/` 目录项不再被误当成图片文件。

### 4.3 专业符号和 Word 公式输出

- 通过 `AcademicExpression` 与统一渲染契约处理公式、方程、数值单位、向量、矩阵、反应式和学科符号。
- 中间层保留原文；规范化值只用于比较、审计和缓存，不在审计阶段擅自重写答案。
- 正式链路为 `LaTeX -> MathML -> Microsoft mathml2omml.xsl -> Word OMML`。
- `app/omml.py` 在正式转换失败时显式报错，不再静默把公式变成普通文字。
- 最小自研转换器只有显式设置 `ANSWER_BOOK_ALLOW_DEGRADED_OMML_FALLBACK=1` 时才用于环境排查。

### 4.4 专业图和生图边界

- 专业图 schema 必须提供真实数据；缺少曲线点、峰值、相区、工艺步骤、结构或必需标签时拒绝构建。
- 删除热处理、相图、XRD、TTT/CCT、应力应变、热分析、高分子、陶瓷等 renderer 中的演示曲线、默认峰值和虚构参数。
- 程序不再仅根据题干关键词猜测一幅预置专业图；旧任务中已显式保存的 schema 仍可兼容渲染。
- 只有确定性 schema 校验通过的图才能使用对应专业视觉 QA 策略。
- 可参数化的曲线、流程和结构图优先由程序绘制；无法完全确定化的创作图再使用图片模型。
- 原题图上的标注优先保留原图并叠加，不重画信息可能变化的新图。

### 4.5 OCR、内容质量和计算一致性

- `app/ocr_corrections.py` 把模型声明的 OCR 修正只记录为候选。
- 只有带精确 JSON 路径、字符区间、原文和替换文本的 `verified_ocr_corrections` 才实际修改内容。
- 删除递归全局 `str.replace`，避免一个判断改掉全文所有同字符串。
- `app/calculation_consistency.py` 检查最终答案、步骤和结果公式之间的高置信度矛盾。
- 质量治理区分确定性后置条件、启发式告警和模型意见；新规则先 shadow 运行，不自动升级为硬门禁。

### 4.6 任务可靠性和可观测性

- 真题和生题任务增加分阶段状态、容量控制、队列、worker、持久化作业、诊断和调用报告。
- 逐题检查点使用内容指纹；题号不变但题干、子问、图片或规划变化时，只重做不匹配题。
- 恢复区分可复用、待重做、缺失、重复、外来和无效片段；旧进度不能覆盖更完整的持久化结果。
- 取消、失败和完成等终态不能被迟到心跳、进度或模型响应覆盖。
- 控制文件和检查点使用临时文件、`fsync` 和原子替换；服务重启后的 detached 任务按安全计划重新入队。
- API 返回结构化错误；前端按服务端 capability 决定操作，不自行推断任务状态。

### 4.7 Word 交付和用户体验

- 真题答案与生题 Word 分别使用明确文档契约，保留现有页面、字体、字号、编号和区块结构。
- 项目字体只注入单次 LibreOffice 子进程，不安装或修改系统字体。
- 渲染审计检查页数、页眉、裁切、公式、图片、字体和最终交付契约。
- 结果视图区分可复用、待重跑和未评估题；任务状态、质量状态和下载权限使用同一契约。

## 5. 成熟组件的取舍

已使用或保留：

- Microsoft Word `omml2mathml.xsl` / `mathml2omml.xsl`：公式结构转换适配器；
- `python-docx` + `lxml`：文档容器和 XML 顺序/结构处理；
- `latex2mathml`：LaTeX 到 MathML；
- Matplotlib/Pillow：确定性图和图像处理；
- LibreOffice/PDF 工具：最终 Word 的真实视觉检查。

未盲目引入：

- AnyDoc/Docling：只可能作为复杂 PDF/扫描件的可选 ingestion adapter，不替换业务主流程；
- Graphviz：只有流程图布局 A/B 明显更优才引入；
- RDKit/Pint：只能按需加载为学科能力，不能进默认链路；
- 新 OCR 引擎：必须比较位置级置信信息、公式和专业符号保真度；
- 新任务队列：现有持久化队列和恢复契约没有被真实数据证明不足前不更换。

## 6. 与线上版本的分环节 A/B

未读取线上当时代码快照前，不宣称线上一定存在某个缺陷。下表规定候选版的应有表现和比较指标。

| 环节 | 当前优化候选的契约 | A/B 指标 |
| --- | --- | --- |
| DOCX 输入 | 段落/表格顺序与 Word 正文一致 | 错位、丢表、重复段落 |
| 输入公式 | OMML 转结构化 MathML；降级可见 | 公式总数、结构化数、降级数、符号损坏 |
| 输入图片 | 正文锚点与视觉输入序号一致 | 图片丢失、错位、错绑、超限告警 |
| 题目结构 | 无空父级、错圈号、错序和题答错配 | 主题/子问数、层级错误、附件绑定 |
| 专业符号 | 通用核心不含材料样题规则 | 符号损坏、无关学科误触发 |
| 专业图规划 | 缺少 schema 必需数据时拒绝构建 | 虚构数据、缺字段拒绝、有效图成功率 |
| 生图/绘图 | 确定图走代码，创作图走图片模型 | 成功率、重试、耗时、语义错误 |
| OCR | 候选与已验证应用分离 | 候选数、应用数、误改数 |
| 输出公式 | OMML 失败可追踪，不静默文本化 | 公式丢失、静默降级、交付拦截 |
| 任务恢复 | 只复用身份和内容指纹一致片段 | 重复调用、错复用、恢复后状态 |
| Word 交付 | 原格式契约和渲染门禁保持 | 丢图、公式、字体、页面、页眉、编号漂移 |
| 用户体验 | 进度、质量、恢复和下载权限真实 | 等待时间、误导状态、额外操作数 |

## 11. A/B 择优方法

1. 先比较无模型输入解析、结构、公式、图片和 Word 契约，排除模型随机性。
2. 再使用相同 provider/model 做配对真实任务；只有结果有争议时才有限重复。
3. 硬回归（漏题、错序、公式损坏、丢图、错位、状态错误、无法恢复）一律不接受。
4. 质量提升必须同时考虑耗时、模型调用、重试、部署难度和失败降级。
5. 对每个新组件记录：替换哪个旧模块、能否关闭、失败后走什么路径、是否影响无关学科。
